# RepoTrace 为什么存在

## 我想解决的那一分钟

很多 Bug 的第一反应其实不是“怎么写修复代码”，而是：

> 这个问题以前是不是发生过？

真实项目里，答案通常散在不同地方。Issue 写现象，PR 写修复，Commit 写具体改动，评论里可能才有根因，文档又补充了正确行为。GitHub 的搜索能找到单条记录，但它不会替开发者把这些记录串成一次调查。

我想把这段工作缩短。

RepoTrace 的第一版只做一件事：开发者给出一个故障描述、错误码或异常片段，系统去项目历史中找相关证据，并回答三个问题：

1. 历史上有没有相似问题；
2. 当时的根因是什么；
3. 最后怎么处理。

如果第三个问题没有足够证据，答案应该停在“目前能确认到这里”，而不是继续补一个听起来合理的结论。

## 典型使用流程

假设一个项目升级后偶发 401：

```text
开发者输入
“升级后登录偶发 401，refresh token 并发时更明显”

        ↓

RepoTrace 检索历史 Issue / PR / Commit / docs

        ↓

找到：
Issue #184：并发 refresh 时旧 token 被复用
PR #201：增加 single-flight refresh lock
Commit abc123：修改 refreshAccessToken

        ↓

返回调查结论 + 证据链接 + 置信度
```

使用者节省的主要是“翻历史记录”和“确认上下文”的时间。对于刚接手项目的人，这类时间往往比真正写那几行修复代码更长。

## 为什么没有把它做成通用知识库

“上传文档然后问问题”已经有很多成熟产品。RepoTrace 更适合把精力放在软件工程里特有的信息结构上：

- Issue 有编号、状态、标签和讨论语义；
- PR 有“是否合并”这个很强的修复信号；
- Commit 能把抽象描述落到具体变更；
- 错误码、函数名、路径、配置项通常需要精确匹配；
- 中文开发者提问，历史记录又可能主要是英文。

这些特点决定了检索和排序不能只照搬普通文档 RAG。

## V1 的边界

当前版本明确不做这些事：

- 自动修改代码；
- 自动开 PR；
- 大规模 Code Graph；
- 跨多个仓库同时调查；
- 实时增量同步所有 GitHub 事件；
- 复杂多 Agent 自由规划。

这些能力以后都可能有价值，但放进第一版会稀释“历史故障调查”这个核心场景。

## 怎么判断这个项目有没有用

最终不能靠 Demo 漂亮来判断。

对 RepoTrace 来说，至少要测两类指标：

### 检索是否找到了正确历史记录

- Hit Rate@K
- MRR
- 后续加入真实数据后再补 nDCG、Recall@K

### 调查结果是否真的帮助开发者

后续需要在真实仓库做人工对照实验：

- 人工 GitHub 搜索耗时；
- RepoTrace 调查耗时；
- 正确 Issue / PR 是否进入 Top K；
- 根因回答是否被证据支持；
- 使用者还需要手动翻多少条记录。

V1 先把第一类指标做成可重复回归，第二类留给真实仓库 benchmark。
